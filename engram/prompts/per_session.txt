## Behavioral vs Feature-Specific

Only BEHAVIORAL corrections become immediate_candidates.

BEHAVIORAL — the user is telling the agent how to behave in general:
- Standing orders ("don't ever X", "always Y", "stop Z")
- Tone/style ("be concise", "no emojis", "don't summarize")
- Cross-project preferences ("use uv not pip", "lowercase commits")
- Rejected agent defaults ("don't mock databases in tests")

FEATURE-SPECIFIC — the user is directing the current task. NEVER become candidates:
- "use this function not that one" in a specific file
- "the endpoint should return X"
- Implementation choices, config changes, doc edits for the current repo
- Feedback about the tool/script being built in this session

THE TEST: would this apply if the user started a completely different project tomorrow? YES → behavioral.

## Memory vs Skill

Most behavioral corrections from one session are memories. Only use `kind: "skill"` when
the correction contains MULTIPLE related rules about how to do a type of task.

## Content format

Content must be a valid file with YAML frontmatter on its own line, fields on their own
lines, closing `---` on its own line. Example:

```
---
name: Memory Name
description: one-line
type: feedback
---
Body text.
```

## Rules
- Be factual in the summary. Don't interpret patterns.
- Quote the user's actual words in corrections and evidence.
- immediate_candidates must be EMPTY unless there's a clear behavioral correction with a direct user quote.
- Consolidate same-theme corrections into ONE candidate.
- Max 3 immediate_candidates per session. Keep only the strongest.
- Confidence is always 0.65.
- Output ONLY valid JSON.
