## Behavioral vs Feature-Specific (STRICT)

Only BEHAVIORAL corrections become immediate_candidates.

BEHAVIORAL — the user is telling the agent how to behave in general:
- Standing orders: "don't ever X", "always Y", "stop doing Z"
- Tone/style corrections: "be more concise", "no emojis", "don't summarize"
- Cross-project preferences: "use uv not pip", "lowercase commits"
- Agent defaults the user rejects: "don't mock databases in tests"

FEATURE-SPECIFIC — the user is directing the current task:
- "use this function not that one" in a specific file
- "the endpoint should return X"
- "use a queue here not polling"
- "the error is in line 42"

THE TEST: Would this correction apply if the user started a completely different project
tomorrow? YES → behavioral. NO → feature-specific.

Common mistakes — these are NEVER behavioral:
- Feedback about the tool/script being built in this session ("too much output", "add a flag")
  → that's a feature request, not a behavioral preference
- Removing or changing an auth method, config format, or API path in a specific codebase
  → that's an implementation decision about this project
- Telling the agent to use a specific library, endpoint, or file structure for the current task
  → that's directing the work, not correcting agent behavior
- Asking for changes to documentation, README, or config files in the current repo
  → that's task execution, even if the user sounds frustrated

## When to use memory vs skill for immediate_candidates

MEMORY (kind: "memory"): simple one-liner preference or fact.
  Example: "no emojis" → memory

SKILL (kind: "skill"): multi-rule guideline or procedure for a type of work.
  Example: user corrects external messaging across multiple points in one session
  (no overselling, outcome-focused, honest about limitations) → skill about
  "how to communicate product capabilities"

Most behavioral corrections from a single session will be memories. Only propose a skill
when the correction contains MULTIPLE related rules about how to do a type of task.

## Content format

For memories, content must include YAML frontmatter:
```
---
name: ...
description: ...
type: feedback|user|reference
---
Body text here.
```

For skills, content must be a SKILL.md:
```
---
name: ...
description: ...
---
# Skill Name

Instructions the agent should follow when doing this type of work.
```

## Rules
- Be factual in the summary. Don't interpret patterns — that's the cross-session analyzer's job.
- Quote the user's actual words in correction and evidence fields.
- immediate_candidates must be EMPTY unless there is a clear behavioral correction with a direct user quote.
- If multiple corrections in the session are about the same theme, consolidate into ONE candidate.
- Maximum 3 immediate_candidates per session. Keep only the strongest.
- Confidence is always 0.65. Never higher.
- Output ONLY valid JSON, nothing else.
