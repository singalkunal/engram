## What's NOT worth learning
- Things already in the code (bug fixes, product decisions reflected in implementation)
- Things in git history (who changed what, when)
- Tool/platform limitations (file size limits, token caps, EISDIR errors, context window issues)
- Agent infrastructure issues (model timeouts, API errors, tool failures)
- One-off product decisions that are now in the code
- Generic observations ("user prefers good UI", "user focuses on quality")
- Echoing user instructions back as preferences

## What IS worth learning

As SKILLS (propose when you see a multi-rule pattern for how to do a type of work):
- Recurring workflows: "When writing user-facing copy: no fluff, no overselling, let the product speak"
- Communication guidelines: "When describing capabilities externally: be honest about what AI can verify"
- Coding conventions that override defaults: "Use create_ch_client() not get_ch_client()"
- Architectural patterns: "Build-time injection over runtime fetches for slow-moving config"

As MEMORIES (propose when you see a simple one-liner preference or fact):
- "Never mock databases in integration tests"
- "No emojis in code or comments"
- "Lowercase commit messages, no conventional prefixes"

## COHERENCE TEST for skills (critical — apply this strictly)

A skill is NOT just "multiple corrections about the same feature/area". It is a coherent
guideline where every rule reinforces ONE transferable principle.

Before proposing a skill, write the principle in ONE sentence. Then check: do ALL the
corrections in the evidence naturally follow from that principle? If you have to say
"various fixes in X", "assorted decisions about Y", or "mixed corrections in the Z area",
it's a TOPIC CLUSTER, not a skill. Reject it.

BAD (topic cluster — do not propose as skill):
- "database layer": "use connection pooling" + "add query timeouts" + "prefer UUIDs over ints"
  → three unrelated DB decisions. No shared principle, just the same subsystem.
- "settings page UI": "add dark mode toggle" + "reorder sections" + "shrink the header"
  → specific tweaks for one page. Wouldn't apply to a different page.
- "API endpoints": "add /status route" + "rename users to accounts" + "add rate limit"
  → touched the API but no common rule connects them.

GOOD (coherent principle — propose as skill):
- copywriting: "no hype words" + "outcome-focused" + "cut fluff" + "no emojis"
  → principle: "write professional user-facing copy that lets the product speak."
     Each rule follows directly.
- testing: "never mock DBs" + "use real fixtures" + "seed from production snapshots"
  → principle: "integration tests must hit real systems, not mocks."
- review: "check before approving" + "don't oversell" + "only claim what's verified"
  → principle: "be honest about what was actually done."

If the evidence is a mix of unrelated corrections that happen to share a keyword, EACH one
is either its own memory or nothing. Do not bundle them into a fake skill.

## Skill path — match scope to principle, not evidence

The skill's `path` should reflect its principle's SCOPE, not the evidence's location.
Look at the existing skills layout below to see how THIS user organizes skills. Pick the
directory whose scope matches your principle:
- If the principle applies broadly across domains (copywriting, external communication,
  thinking frameworks, testing philosophy), use the broadest/shared directory available.
- Only narrow to a domain-specific directory when the principle is genuinely
  domain-specific (e.g., a backend-only coding convention).

A principle that would apply on a completely different codebase should NEVER sit in a
domain-specific subfolder just because the evidence happened to come from that domain.
